# AWS Production Cell v1

This bundle creates one isolated, multi-tenant Graviton cell from an empty data store. It is an executable deployment contract, not evidence that this repository has already passed AWS capacity or fault qualification.

## What it creates

- three public and three private subnets across three available zones;
- one NAT gateway per zone and an S3 gateway endpoint;
- one public TLS Application Load Balancer;
- one singleton Shardcake manager and three stable, independently replaceable Graviton node services on ECS Fargate;
- private Cloud Map DNS identities for the manager and every node;
- a private Multi-AZ PostgreSQL 16 instance with an AWS-managed master password;
- a private three-node, Multi-AZ ElastiCache Valkey replication group for cluster-wide transfer admission;
- separate KMS-encrypted S3 block and resumable-staging buckets;
- a KMS-encrypted Secrets Manager shell for runtime credentials;
- least-purpose execution and S3 task roles, CloudWatch logs, health checks, and deployment circuit boundaries;
- an isolated initial tenant whose UUID must match the organization claim in the qualification token.

The cell uses external OIDC authentication. Graviton owns byte identity, streaming, manifests, block placement, deduplication, verification, repair, and storage admission. It does not own users, login, or document semantics.

## Deliberate boundaries

- Runtime secrets are generated by `operator.sh` and written directly to Secrets Manager. Terraform creates the secret resource but never receives a secret value, so credentials do not enter Terraform state.
- Terraform creates Valkey with TLS and KMS encryption but no initial password. With long-running services still disabled, `operator.sh` installs the Secrets Manager password using ElastiCache's `SET` strategy, waits for availability, and verifies AUTH, TLS, at-rest encryption, automatic failover, Multi-AZ, three members, and the primary endpoint. Terraform refuses `bootstrap_complete=true` until the provider observes AUTH enabled.
- The RDS master password is generated and retained by RDS through Secrets Manager.
- Long-running services are not created until the one-shot schema bootstrap and runtime-role verification succeed.
- Every Graviton image and bootstrap image must use an immutable SHA-256 digest.
- Shardcake nodes use separate ECS services and Cloud Map names. A replacement never overlaps another task with the same node identity.
- The first tenant is isolated. Cross-tenant physical deduplication remains disabled.
- The application task has no database control-plane credential. Tenant policy changes require a separate operator path.
- Authentication and authorization remain external. The cell accepts a reviewed OIDC issuer and token capabilities.

## Prerequisites

- Terraform 1.5.7 or newer;
- AWS CLI, Docker, `jq`, OpenSSL, and Bash;
- an existing, versioned S3 Terraform-state bucket with locking and KMS encryption;
- an ACM certificate in the selected region;
- a reviewed immutable Graviton image digest;
- an OIDC issuer, audience, JWKS URI, and CORS origin;
- AWS permissions to create the resources in `terraform/`.

The stack creates billable resources including three NAT gateways, a Multi-AZ RDS instance, a three-node ElastiCache Valkey replication group, Fargate tasks, an ALB, KMS keys, and S3 storage. `operator.sh validate` and `operator.sh plan` are read-only. `operator.sh infra` and `operator.sh up` create external resources and charges.

## Validate without AWS credentials

```bash
./deploy/aws-cell-v1/operator.sh validate
```

This initializes providers and modules with the backend disabled, checks Terraform formatting and structure, and checks every shell entrypoint.

## Configure

Copy the examples outside source control or to the ignored local names:

```bash
cp deploy/aws-cell-v1/terraform/production.tfvars.example \
  deploy/aws-cell-v1/terraform/production.tfvars
cp deploy/aws-cell-v1/terraform/backend.hcl.example \
  /secure/path/graviton-backend.hcl
```

Replace every placeholder. The initial tenant UUID must be the exact lowercase organization UUID emitted by the OIDC token used for qualification.

```bash
export GRAVITON_TF_VAR_FILE="$PWD/deploy/aws-cell-v1/terraform/production.tfvars"
export GRAVITON_TERRAFORM_BACKEND_CONFIG=/secure/path/graviton-backend.hcl
export GRAVITON_OIDC_ISSUER=https://identity.example.com/
export GRAVITON_OIDC_AUDIENCE=graviton
export GRAVITON_OIDC_JWKS_URI=https://identity.example.com/.well-known/jwks.json
export GRAVITON_CORS_ALLOWED_ORIGINS=https://storage.example.com
```

Review the plan:

```bash
./deploy/aws-cell-v1/operator.sh plan
```

## Bootstrap a new cell

After explicit approval for the AWS resources and estimated charges:

```bash
./deploy/aws-cell-v1/operator.sh up
```

The operator performs six fail-closed stages:

1. Create networking, KMS, S3, RDS, ElastiCache Valkey, ECS, ALB, IAM, logs, and empty secret resources with long-running services disabled.
2. Generate the application password, Shardcake token, manifest HMAC key, and Valkey password locally, then send one JSON value directly to Secrets Manager. A safe retry verifies and reuses the complete existing value instead of rotating it.
3. Install Valkey AUTH from a protected temporary JSON request, wait for the replication group, and verify the complete encrypted Multi-AZ contract. The password is absent from command arguments and Terraform state.
4. Build the bootstrap container, push it to the cell ECR repository, and resolve its immutable digest.
5. Run one private Fargate task that applies the checksum-locked schema, creates the constrained runtime role, verifies its exact privileges, and provisions the initial isolated tenant.
6. Create the singleton manager and stable node services, then wait for every ECS service to stabilize.

The secret seeding stage refuses to replace an existing `AWSCURRENT` value. Credential rotation needs a separate dual-key or coordinated-password runbook.

Create a Route 53 alias from the certificate hostname to the emitted ALB DNS name. The ALB redirects HTTP to HTTPS, terminates TLS, overwrites forwarding headers, and sends HTTP only inside the private task network.

## Qualify the exact deployed cell

Use a bearer token with the initial tenant organization and blob write, read, metadata, verify, and inspection capabilities. Then run:

```bash
export GRAVITON_AWS_BASE_URL=https://storage.example.com
export GRAVITON_BEARER_TOKEN='short-lived-token'
./deploy/aws-cell-v1/qualify.sh
```

The gate sends a real 32 MiB stream through the ALB, OIDC boundary, Shardcake locality, PostgreSQL manifests, and S3 blocks. It verifies byte-exact download and server-side content verification, uploads the identical payload again and requires zero fresh blocks, confirms the same content ID, and proves an exact 1 MiB HTTP range. Supplying a path as the first argument qualifies a representative corpus item instead of generated random data.

Retain the JSON result with the Terraform revision, Graviton image digest, AWS account and region, RDS configuration, task sizes, and CloudWatch interval. One successful 32 MiB gate proves this lifecycle, not customer-scale capacity.

## Required acceptance before customer traffic

Run and retain all of the following against the exact cell:

- concurrency sweeps at expected and two-times expected upload and download load;
- at least one payload larger than the resumable part ceiling and one representative maximum document;
- node replacement during active resumable uploads;
- Valkey primary failover during queued and active transfer leases, including renewal, expiry, fencing, and recovery telemetry;
- temporary Valkey unavailability proving new acquisitions fail closed while every process remains within its hard local byte ceiling;
- singleton manager replacement and shard reassignment;
- one-zone task and network impairment;
- RDS failover while reads, new uploads, and resumed uploads are active;
- S3 throttling and injected timeout behavior;
- coordinated RDS snapshot plus S3 recovery into a separate cell;
- garbage collection under the backend-wide maintenance lease;
- a sustained soak with heap, direct memory, blocked threads, database pool wait, S3 retries, ALB latency, and deduplication metrics retained.

Do not call the AWS topology production-qualified until those results meet explicit SLO and recovery thresholds. The checked-in local MinIO and PostgreSQL tests remain useful protocol evidence but are not AWS fault evidence.

## Operations and maintenance

- Keep the manager desired count at one. Its database lease rejects accidental overlap.
- Replace one stable node service at a time. The ECS service uses `0/100` replacement so the same Shardcake identity never overlaps itself.
- Keep at least two healthy node services during planned work.
- Run schema bootstrap before enabling a new image. The migration checksum rejects drift in migration `001`.
- Use the same maintenance namespace for every node in the cell.
- Treat RDS and both S3 buckets as one recovery set. A database snapshot without the reachable block versions is not a valid restore.
- Review retained S3 versions and lifecycle cost. Block deletion remains a coordinated Graviton maintenance operation.
- Keep application logs free of bearer tokens, secret JSON, and payload bytes.
- Retain the bounded admission decision stream and Prometheus occupancy metrics. Treat predictive policy changes as a separate reviewed controller with explicit override floors, ceilings, and rollback.

The infrastructure follows AWS guidance to place compute and databases in private subnets across multiple zones and expose only the load balancer. See the [Amazon EKS subnet guidance](https://docs.aws.amazon.com/eks/latest/best-practices/subnets.html) for the same public-ingress/private-compute network principle and the [Application Load Balancer documentation](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) for ALB behavior.
